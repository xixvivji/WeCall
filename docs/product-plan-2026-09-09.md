# WeCall B2B 통합 기획안
## 식품 유통사의 회수 요청 분석·영향 추적·대응 관리 AI 서비스

**작성 기준: 2026년 9월 9일 / 상태: 기획·검증 단계**

이 문서는 첨부된 「붙여넣은 마크다운(1).md」의 초기 기획안과 후속 수정·검증 논의를 통합한 것이다. 고객 수요, 데이터 확보 가능성, 성능 개선은 아직 검증된 성과가 아니다. 기능 설명은 구현 목표이며, 실제 개발 완료를 의미하지 않는다.

## 1. 가장 먼저 이해할 서비스 개념

**WeCall B2B는 식품 유통사가 회수 통보를 받은 뒤, 외부 문서와 내부 상품·입출고 기록을 대조해 회수 대상과 영향 범위를 확인하고, 담당자의 조치와 증빙을 관리하도록 돕는 AI 서비스다.**

회수 사실을 처음 알려주는 것이 중심이 아니다. 이미 통보받은 사건에 대해 “우리 회사의 어떤 상품인가, 어떤 제조분이 대상인가, 어디에 얼마나 남아 있는가, 기록으로 확인되는 출고는 무엇인가, 무엇을 추가 확인하고 누가 처리해야 하는가”를 정리하는 서비스다.

우리는 유통사에 소프트웨어를 제공한다. 직접 식품을 판매·보관·배송하거나 물리적인 회수를 수행하지 않는다. [^source01]

| 항목 | 현재 기획 기준 |
| --- | --- |
| 프로젝트명 | WeCall B2B |
| 초기 고객 | 국내 포장 가공식품을 취급하며 내부 기록을 내보낼 수 있는 유통사 |
| 주 사용자 | 품질관리·상품관리 담당자 |
| 협업 사용자 | 구매·물류·판매 채널·고객상담 담당자 |
| 업무 시작 | 공급사 회수 요청, 공식 공지, 사내 품질팀 통보 수신 |
| 업무 종료 | 미확인·미처리 사항을 검토하고 담당자가 내부 종료 승인 |
| 핵심 입력 | 회수 문서, 상품·입고·재고·출고 데이터, 추가 증거 문서 |
| 핵심 결과 | 근거가 있는 대상 판정, 영향 범위, 확인 필요 항목, 조치·증빙 이력 |
| 첫 검증 방식 | 공개 회수 사례와 가상 기업 데이터로 동작·정확도를 평가 |

초기 고객 범위는 후속 검토안을 따랐으며, 사용자와 업무 시작점은 초기안의 구성을 유지했다. [^source02]

## 2. 초안에서 달라진 부분과 이번 정리의 기준

첨부 자료에는 처음 제안한 범위와 나중에 좁힌 범위가 함께 있다. 아래 항목은 **후속 검토 방향을 이번 통합안의 기준으로 채택한 것**이지, 고객 검증을 마친 확정 사항은 아니다.

| 항목 | 초기 기획 | 후속 수정 방향 / 통합 기준 |
| --- | --- | --- |
| 고객 범위 | 식품·건강기능식품 유통사 | 국내 포장 가공식품 유통사로 우선 제한. 건강기능식품 등은 초기 제외 |
| 제품의 중심 | 상품 대조와 회수 대응 전반 | 기존 기록과 외부 문서 사이의 증거 대조·예외 처리에 집중 |
| 세트상품 | 1단계 구성 추적 지원 | 실제 투입 제조분 기록이 있을 때 추가하는 후순위 기능 |
| 모의 회수 | 현재 범위에 자동 추가하지 않음 | 재사용 가능한 확장 후보지만 수요 검증 전 필수 기능으로 넣지 않음 |
| 제조번호 누락 | 누락 항목을 중요하게 점검 | 해당 공지가 요구하는 식별 조건이 무엇인지 먼저 판단 |

핵심은 **“모든 기능을 포함한 회수 플랫폼”보다 “한 사건을 기록과 근거에 따라 끝까지 처리하는 첫 버전”**이다. [^source03]

## 3. 해결하려는 문제

### 3.1 문제 정의

> 회수 요청에 담긴 상품·대상 조건을 기업의 서로 다른 기록과 연결하고, 확인되지 않은 부분과 후속 작업을 관리하는 데 드는 시간을 줄인다.

회수 사실을 아는 것과 대응에 필요한 범위를 확인하는 것은 별개다. 기획에서 조사하려는 어려움은 다음과 같다. 아래 내용은 모든 유통사에 존재한다고 확인된 문제가 아니라 **타깃 고객에게 검증할 상황**이다. [^source04]

| 업무 | 예상되는 어려움 | WeCall이 지원하려는 내용 |
| --- | --- | --- |
| 상품 확인 | 공급사 명칭과 내부 상품명이 다름 | 내부 상품 후보와 일치·상충 근거 제시 |
| 대상 범위 확인 | 같은 상품의 제조번호·날짜·규격이 다름 | 승인된 조건에 따른 대상·비대상·확인 필요 분리 |
| 영향 추적 | 입고·재고·출고 자료가 서로 분리됨 | 실제 연결 기록을 따라 영향 범위 조회 |
| 불확실성 해소 | 제조번호 누락 또는 문서와 DB 충돌 | 부족한 정보와 필요한 증거 표시 |
| 대응 협업 | 부서·물류사·판매처별 결과 취합 필요 | 담당자·상태·처리 시각·증빙 관리 |

### 3.2 근거가 있는 부분과 없는 부분

첨부 검토 자료는 SK스토아의 수작업 상품 대조 개선 사례와 회수 업무 매뉴얼을 근거로, **상품 대조와 회수 대응 업무가 존재한다**고 설명한다. 다만 그것만으로 우리 고객의 가장 큰 병목이 무엇인지, 별도 도구에 돈을 낼지는 확인되지 않는다.

현재 남아 있는 핵심 질문은 세 가지다. **실제로 중요한 병목인가, 필요한 내부 기록을 확보할 수 있는가, 기존 방식보다 시간과 오류를 줄이는가.** [^source05]

## 4. 누구에게 제공할 것인가

### 4.1 초기 고객 가설

**여러 공급사에서 포장 가공식품을 매입하고, 자체·위탁창고와 여러 판매 채널을 운영하며, 상품·입고·재고·출고 기록을 제공할 수 있는 유통사**를 우선 조사한다.

회사 규모 자체보다 “기록은 있지만 표현·코드·단위가 달라 연결과 확인이 어렵다”는 조건이 중요하다. [^source06]

| 도입 가능성을 확인할 조건 | 이유 |
| --- | --- |
| 상품과 거래 정보가 여러 곳에 존재 | 연결 업무의 필요성을 확인할 수 있음 |
| 사건에 필요한 제조분·날짜 정보가 존재 | 실제 대상 판별에 쓸 근거가 있어야 함 |
| 재고·출고 기록과 연결 관계가 존재 | 추적 가능한 범위를 확보해야 함 |
| 반복적인 추가 확인이 발생 | 시간·오류 개선을 측정할 수 있음 |
| 파일 제공 또는 제한적 연동이 가능 | 제품 적용이 가능해야 함 |

### 4.2 초기 제외 또는 도입 가치가 낮은 고객

기존 시스템에서 이미 대상과 출고를 빠르게 확인하는 회사, 직접 확인하는 편이 빠를 정도로 거래가 적은 회사, 필요한 기록이 없는 회사는 적합성이 낮다. 회수 업무 빈도가 낮고 구매 의사가 없는 경우에도 구독 수요를 전제하지 않는다.

재고와 주문을 통제하지 않는 중개 전용 플랫폼, 복잡한 원재료 혼합·가공 추적, 의약품·건강기능식품, 전국 단위 소비자 추적은 초기 범위에서 제외한다. [^source07]

## 5. 사용자별 역할

| 사용자 | 기획한 업무 |
| --- | --- |
| 품질·상품관리 | 사건 등록, 원문·회수 조건 검토, 상품 연결과 대상 확인 |
| 구매 | 공급사 정보, 제조번호, 입고 근거 확인 |
| 물류 | 창고 위치·잔량 확인, 격리·출고보류 작업과 증빙 기록 |
| 판매 채널 운영 | 채널별 상품 확인, 판매보류 처리 결과 기록 |
| 고객상담 | 연결이 확인된 주문 확인, 승인된 안내문 활용, 안내 결과 기록 |
| 관리자 | 데이터 등록, 사용자 권한, 사건 현황 관리 |

첫 버전은 **검토자와 실행 담당자 두 역할**부터 구현한다. 부서별 세분화는 실제 운영 권한 체계가 확인된 뒤 확장할 수 있다. [^source08]

## 6. 전체 서비스 흐름

**기업 데이터 준비 → 사건 등록 → 조건 검토 → 상품 연결 → 대상 판별·영향 추적 → 증거 보완 → 조치·증빙 → 내부 종료**

이 흐름의 중간중간에 담당자 검토가 들어간다. AI 분석 결과가 곧 최종 대상 확정이나 조치 승인을 의미하지 않는다. [^source09]

### 6.1 기업 데이터 준비

상품·입고·재고·출고 파일을 등록한다. 첫 버전은 정해진 CSV 양식으로 시작한다.

필수 필드 누락, 존재하지 않는 상품 ID, 중복 기록, 날짜·수량 형식 오류, 사건 판정에 필요한 정보, 주문·출고 연결 상태를 점검한다. 사용자에게 데이터 기준 시각과 분석 가능한 범위를 보여준다.

**데이터 오류나 누락을 회수 비대상으로 처리하지 않는다.** 업로드 성공과 추적 가능 상태도 구분해야 한다. 예를 들어 상품 목록은 정상 등록됐지만 출고 제조분 연결은 없을 수 있다. [^source10]

### 6.2 회수 사건 등록

| 입력 경로 | 내용 | 첫 버전 범위 |
| --- | --- | --- |
| 공급사 요청 | 이메일 본문·첨부 문서 | 본문 붙여넣기 우선 |
| 공식 공지 | 공개 공지 본문·문서 | 검증된 샘플 공지 선택·등록 |
| 사내 품질팀 통보 | 확인된 대상 정보 | 직접 입력 경로로 설계 |

출처 유형, 발신자, 발표일, 원문, 담당자를 사건과 함께 관리한다. 출처가 다르거나 내용이 상충하는 자료는 자동으로 같은 사건으로 합치지 않는다.

이메일 계정 연결, 모든 사이트의 자동 수집은 첫 버전에서 제외한다. [^source11]

### 6.3 회수 조건 추출·검토

제품명·제조사·규격, 제조번호, 제조일자·소비기한, 대상·예외 조건, 회수 사유를 추출한다. 원문과 추출 결과를 함께 보여주고 담당자가 수정·승인하도록 한다. 원래 추출값과 수정 이력을 보존한다.

구조화된 입력은 코드로 읽고, 문장·표의 관계처럼 해석이 필요한 부분에 AI를 사용한다. 모든 입력을 무조건 AI에 보내는 구조로 만들지 않는다. [^source12]

### 6.4 자사 상품 연결

**정확한 식별자·승인된 연결정보 → 키워드·임베딩 후보 검색 → AI 속성 비교 → 담당자 확인** 순서로 진행한다.

제품명만 보지 않고 제조사, 규격·포장 단위, 식품유형, 원문에 있는 보조 정보를 함께 비교한다. 결과는 연결 확인, 후보 검토 필요, 현재 데이터에서 후보 미발견으로 구분한다.

**후보 미발견은 미취급 확정이 아니다.** 상품 데이터 누락이나 표현 차이 때문에 찾지 못했을 가능성을 남긴다. [^source13]

### 6.5 대상 판별과 영향 추적

연결된 상품의 기록에 회수 조건을 적용한다. 비교와 수량 계산은 코드·DB가 담당한다.

| 판정 | 의미 |
| --- | --- |
| 대상 확인 | 필요한 정보가 있고 해당 조건을 충족 |
| 비대상 확인 | 필요한 정보가 있고 해당 조건을 충족하지 않음 |
| 확인 필요 | 정보 누락·충돌 등으로 판단할 수 없음 |

상품 연결과 제조분 판별은 별도 결과로 저장한다. 이후 실제 기록을 따라 현재 재고, 출고 예정·완료 기록, 연결된 주문을 조회하고 추적이 끊기는 지점도 표시한다. 세트 포장 추적은 후순위다. [^source14]

### 6.6 추가 증거 보완

확인 필요 항목에는 부족한 사실과 필요한 자료를 구체적으로 보여준다. 첫 추가 문서 유형은 입고명세서를 우선 검토한다.

문서에서 제조번호를 읽는 것으로 끝내지 않는다. 어떤 입고 건의 자료인지, 상품·수량이 맞는지, 여러 제조분이 섞였는지, 기존 기록과 충돌하는지, 현재 판단을 바꾸기에 충분한지를 확인한다. 승인된 보완 정보로 결과를 재계산하고 변경 전후를 남긴다. [^source15]

### 6.7 대응 작업과 증빙

재고 격리, 출고보류, 채널별 판매보류 확인, 구매자 안내 준비, 반품·회수 처리 확인, 공급사 추가 확인 등의 작업 초안을 규칙으로 생성한다. 회사가 수정하고 담당자를 지정할 수 있도록 한다.

작업별 상태, 처리 시각, 증빙을 기록한다. 첫 버전은 외부 시스템을 직접 조작하거나 고객에게 자동 발송하지 않는다.

이미 유효한 긴급 조치 지시가 있다면 AI 분석 완료를 기다리게 하지 않는다. 회사 절차에 따른 임시 보류를 기록하면서 분석을 병행할 수 있게 한다. [^source16]

### 6.8 내부 종료와 재검토

미처리 작업, 미확인 대상, 검토되지 않은 증빙을 확인한 뒤 담당자가 내부 종료를 승인한다. 자료가 부족한 항목을 자동으로 완료 처리하지 않는다.

정정 공지나 추가 자료로 범위가 달라질 때는 기존 승인과 작업 중 무엇을 다시 검토해야 하는지 확인할 수 있도록 이력을 유지한다. 여기서 말하는 종료는 제품 안의 **내부 업무 종료**다. [^source17]

## 7. 반드시 구분할 판단과 상태

### 7.1 상품 확인, 대상 판별, 출고 연결은 다르다

상품이 같다는 사실만으로 회수 대상 제조분까지 같다고 볼 수 없다. 입고 제조분을 확인했다고 해당 제조분이 들어간 주문까지 확인되는 것도 아니다.

| 확인한 사실 | 그것만으로 확정할 수 없는 것 |
| --- | --- |
| 바코드·상품코드가 같음 | 특정 제조분까지 회수 대상이라는 결론 |
| 입고명세서에 제조분 A가 있음 | 제조분 A가 어떤 고객 주문으로 출고됐는지 |
| 특정 상품이 세트 구성품임 | 대상 제조분이 실제로 해당 세트에 투입됐는지 |

**추적은 실제 연결 기록이 있는 지점까지만 가능하다.** 출고일이나 선입선출 가정을 이용해 없는 제조분·주문 연결을 확정하지 않는다. [^source18]

### 7.2 제조번호는 모든 사건에서 필수 조건이 아니다

공지가 소비기한으로 대상을 지정했다면 그 조건을 확인하는 것이 우선이다. 제조번호가 없다는 이유만으로 무조건 판단을 막지 않는다.

반대로 제조번호로 범위를 지정한 사건에서는 소비기한이 같다는 사실만으로 대상 제조분이라고 확정하지 않는다. **필수 정보는 해당 사건의 조건에 따라 달라진다.** [^source19]

### 7.3 대상 여부와 조치 상태는 별개다

| 구분 | 가능한 상태 예시 |
| --- | --- |
| 대상 여부 | 확인 필요 |
| 조치 상태 | 임시 보류 완료 |
| 남은 업무 | 공급사 제조번호 확인 |

이처럼 대상이 아직 불확실해도 유효한 지시에 따른 임시 보류는 진행될 수 있다. 반대로 대상이 확정됐어도 실제 격리·판매보류가 끝난 것은 아니다. 이를 하나의 상태값으로 합치지 않는다. [^source20]

## 8. AI 기능 설계

### 8.1 핵심 기능 A: 회수 조건 구조화

문장과 표를 비교 가능한 조건으로 바꾸고 각 조건에 원문 근거를 연결한다.

원문에 제시된 가상 예시는 다음과 같다.

> 제조번호 A01 또는 A02 중 소비기한이 2026년 10월 31일인 제품

이를 `제조번호 ∈ {A01, A02} AND 소비기한 = 2026-10-31`로 표현한다. 초기 지원 범위는 명시적 제조번호, 날짜 일치·범위, 단순 AND·OR다. 복잡한 예외 조건은 검토 대상으로 남긴다. [^source21]

표에서는 값뿐 아니라 **행별 관계**를 보존해야 한다.

| 규격 | 제조분 | 소비기한 |
| --- | --- | --- |
| 100g | A | 1월 31일 |
| 200g | B | 2월 28일 |

올바른 해석은 두 행 각각의 조건을 유지하는 것이다. 열을 독립적인 목록으로만 추출해 존재하지 않는 “100g·제조분 B” 조합까지 포함하면 안 된다. 평가도 글자 인식 정확도뿐 아니라 최종 대상 집합이 맞는지 확인한다. [^source22]

### 8.2 핵심 기능 B: 상품 후보 비교

검색이 후보를 찾고 AI가 속성 차이를 설명하도록 구성한다. 출력에는 후보 상품, 일치하는 속성, 상충하는 속성, 추가 확인 항목, 판단 근거를 포함한다.

“AI 확신도 95%”처럼 검증되지 않은 숫자 대신 “제조사는 일치하지만 규격이 다름”처럼 확인할 수 있는 내용을 보여준다. 최종 연결은 담당자가 검토한다. [^source23]

### 8.3 핵심 기능 C: 추가 증거 해석

입고명세서 등에서 상품·제조번호·날짜를 추출하고 특정 거래 기록과 연결한다. 핵심은 값을 읽는 능력뿐 아니라 **그 증거가 무엇을 증명하는지 구분하는 능력**이다.

입고 기록을 보완한 자료가 출고 제조분 연결까지 증명하는 것은 아니다. 증거가 해결한 범위만 판정을 갱신한다. 첫 버전의 문서 형식은 실제 확보한 샘플을 보고 한 종류로 확정한다. [^source24]

### 8.4 보조 생성 기능

공급사 확인 요청, 구매자 안내문, 사건 요약의 초안을 생성할 수 있다. 수량·상태는 DB 값을 사용하며 담당자 검토 후 활용한다. 보고서의 표·집계는 코드로 생성한다.

기초모델을 새로 학습하는 것을 전제로 하지 않는다. 기존 모델 위에 검색·추출·검증·업무 흐름을 구현하는 기획이며, 자체 개발 언어모델이라고 표현하지 않는다. [^source25]

## 9. AI·코드·사람의 책임 구분

| 업무 | 담당 |
| --- | --- |
| 비정형 문장·표의 조건 해석 | AI가 초안 생성, 사람이 검토 |
| 표현이 다른 상품 후보 비교 | 검색·AI·사람의 단계별 처리 |
| 입고명세서의 정보 추출 | AI가 추출, 거래 연결·충돌·충분성 검토 |
| 명시적 제조번호·날짜 조건 비교 | 코드 |
| 재고·출고·주문 수량 계산 | 코드·DB |
| 확정된 제조분 이동·출고 추적 | 코드·DB |
| 최종 대상 확인·조치·종료 승인 | 담당자 |
| 식품 자체의 위해성 판단 | 제품이 자체 판단하지 않고 공지·확인된 요청을 사용 |
| 외부 판매중지 실행·고객 발송 | 첫 버전 직접 실행 범위에서 제외 |

AI는 없는 제조번호나 거래 관계를 만들어내지 않는다. 이 구분을 백엔드 로직과 화면의 승인 절차 모두에 반영한다. [^source26]

## 10. 데이터 구조와 확보 조건

### 10.1 주요 데이터

다음은 논리적인 데이터 구성이다. 실제 테이블명·컬럼명·제약조건까지 확정된 설계는 아니다.

| 데이터 | 주요 내용 |
| --- | --- |
| 상품 | 내부 ID, 상품명, 제조사, 규격, 바코드 |
| 상품 연결정보 | 공급사·채널 외부 코드, 내부 상품 ID, 승인 이력 |
| 입고 제조분 | 상품 ID, 제조번호, 관련 날짜, 공급사, 입고 건 |
| 재고 | 제조분, 창고·위치, 수량, 보류 상태 |
| 이동·포장 기록 | 위치 이동, 투입 제조분, 포장 수량. 세트 관련 확장은 후순위 |
| 주문·출고 | 주문 ID, 채널, 상품, 수량, 상태, 실제 출고 제조분 |
| 회수 사건 | 출처, 원문, 승인된 조건, 담당자, 상태 |
| 판별 결과 | 대상 기록, 판정, 근거, 부족한 정보, 결과 버전 |
| 증거 문서 | 문서 ID, 원문 위치, 연결된 입고·출고 건 |
| 대응 작업 | 작업 유형·대상·담당자·상태·처리 시각·증빙 |

정확한 출고 대상 추적의 전제는 제조분과 출고를 연결하는 기록이다. 이 관계가 없는 경우 데이터 모델을 만든 것만으로 추적이 가능해지지는 않는다. [^source27]

### 10.2 처음 확보할 자료

전체 고객 DB보다 **한 상품의 입고부터 출고까지 이어지는 작은 자료 묶음**이 우선이다. 상품 목록 일부, 해당 상품 입고·재고·출고 기록, 연결 가능한 입고명세서 한 장으로 구조를 확인한다.

회사·거래처·주문번호는 연결 관계를 유지한 가상 코드로 바꿀 수 있다. 초기 검증에 고객 이름·전화번호는 필요하지 않다. 화면 시연으로 필드만 확인한 경우는 구조 확인이며, 실제 파일 연동 검증과 구분한다. [^source28]

| 확보한 연결 수준 | 지원 가능한 범위 |
| --- | --- |
| 상품 목록만 있음 | 상품 후보 대조 |
| 입고·재고까지만 연결됨 | 제조분 조건 확인과 창고 재고 범위 분석 |
| 제조분·출고·주문까지 연결됨 | 주문·거래처 수준 영향 추적 실험 |
| 필요한 기록이 없음 | 해당 고객에 대한 정밀 추적 기획 재검토 |

합성 데이터로 프로그램을 구현하는 것과 실제 고객의 데이터 확보 가능성을 검증하는 것은 별개다. [^source29]

## 11. 수량 계산과 운영 지표

### 11.1 방지해야 할 계산 오류

| 오류 | 설계 원칙 |
| --- | --- |
| 과거 출고량과 현재 매장 잔량을 합산 | 누적 이동량과 현재 위치별 잔량을 구분 |
| 예약 재고를 실제 재고에 다시 더함 | 동일 재고의 상태와 수량을 중복 집계하지 않음 |
| 박스와 낱개 수 혼용 | 단위와 확인된 환산 관계를 구분 |
| 한 주문의 여러 제조분 중 일부 누락 | 실제 출고 제조분별 연결을 반영 |
| 반품·격리·폐기를 모두 같은 완료 수량으로 취급 | 조치 유형과 실제 물량 상태를 분리 |
| 오래된 CSV를 실시간 재고로 표시 | 재고 데이터 기준 시각을 명시 |

**AI는 수량을 만들어내거나 보고서에 임의의 집계를 쓰지 않는다.** 계산 결과는 검증 가능한 원장과 코드에서 나온다. [^source30]

### 11.2 첫 화면에 보여줄 지표

대상 확정 잔량, 대상 여부 확인 필요 수량, 연결이 확인된 출고 수량, 판매중지 확인 완료 건수, 증빙 검토 대기 건수, 재고 데이터 기준 시각을 우선 사용한다.

작업 완료율을 공식 회수실적과 같은 지표처럼 부르지 않는다. 첨부 검토본도 두 지표를 구분하도록 수정했다. 첫 버전은 내부 운영 지표를 명확히 표시하는 데 집중한다. [^source31]

## 12. 화면 구성

| 화면 | 주요 정보 | 사용자 행동 |
| --- | --- | --- |
| A. 사건 목록 | 진행 사건, 확인 필요 수, 미처리 작업 수, 담당자, 최근 변경 | 사건 선택·현황 확인 |
| B. 데이터 등록 | 샘플 양식, 업로드, 컬럼 연결, 오류·누락, 기준 시각 | 데이터 등록·오류 수정 |
| C. 사건 검토 | 원문 근거, 추출 조건, 상품 후보와 속성 비교 | 조건 수정·상품 연결 승인 |
| D. 영향 범위 | 대상·비대상·확인 필요, 창고·채널·출고 상태, 연결 경로 | 범위 확인·증거 등록·변경 비교 |
| E. 대응 작업 | 담당자별 작업, 진행 상태, 채널별 미처리, 안내문·보고서 | 처리 기록·증빙 검토·결과 출력 |

대회용은 C와 D를 한 사건 상세 화면으로 묶을 수 있다. 핵심 상세 화면에서 **원문 → 조건 → 내부 상품 → 판정 근거 → 연결 범위 → 필요한 작업**을 확인할 수 있도록 한다. [^source32]

## 13. 시스템 구성

| 구성 | 역할 |
| --- | --- |
| 웹 프론트엔드 | 업로드·검토·영향 조회·작업 관리 화면 |
| 백엔드 API | 데이터 검증, 조건 비교, 추적, 승인, 작업·이력 관리 |
| 관계형 DB | 상품·제조분·출고·사건·근거·이력 저장 |
| 파일 저장소 | 원문·입고명세서·증빙 보관 |
| 비동기 작업 처리 | 문서 분석·후보 검색 실행 |
| AI 모델 API | 조건 추출·후보 비교·문서 해석 |
| 검색 인덱스 | 키워드·임베딩 기반 후보 검색 |

관계형 DB와 단계별 처리로 시작하며 그래프 DB나 복잡한 멀티에이전트를 필수로 두지 않는다. 구체적인 언어·프레임워크·모델은 팀 여건에 따라 선택할 항목이다.

분석마다 입력 파일, 모델·프롬프트 버전, 결과, 처리 시간, 오류를 기록해 재현성을 확보한다. 첨부안에는 기술 구성의 역할만 제안되어 있으며 특정 제품 조합까지 확정되어 있지는 않다. [^source33]

## 14. 기존 서비스와 차별화 가설

아래는 **첨부 검토본에 정리된 비교 내용**이다. 경쟁사 전체 기능이나 현재 최신 기능을 새로 조사한 목록은 아니다.

| 비교 대상 | 첨부 자료에서 정리한 내용 | 기획에 주는 의미 |
| --- | --- | --- |
| SK스토아·달파 | 위해상품과 판매상품의 텍스트·이미지 비교 | AI 상품 매칭 자체만으로 차별화하기 어려움 |
| TFOOD ERP | 입출고·재고·제품·거래처 관리와 이력 연계 | 재고 조회 기능만으로는 부족 |
| SAP Global Batch Traceability | 제조분 기록과 유통 경로 연결 | 제조분 추적도 이미 존재하는 기능 |
| GS1 Australia Recall | 거래 파트너 간 회수 정보 공유 | 회수 협업 자체가 새로운 개념은 아님 |

첨부 자료에는 SK스토아의 사후 관리 확장 계획도 언급되어 있다. 따라서 “다른 서비스는 탐지만 하고 우리는 사후 관리까지 한다”는 단정은 쓰지 않는다. [^source34]

검증할 차별화 가설은 다음과 같다.

> **기존 시스템에 기록은 있지만 외부 문서와 표현·코드·단위가 달라 사람이 확인해야 하는 상황에서, 증거 대조와 예외 처리를 더 쉽게 만든다.**

구체적으로 제조분 조건 확인, 부족한 근거 표시, 추가 자료에 따른 판정 갱신, 여러 담당자의 처리 이력, 제한된 파일로 시작하는 도입 방식이 실제로 유리한지 확인한다. 공개 소개에서 기능을 찾지 못했다는 이유만으로 경쟁사에 없는 기능이라고 주장하지 않는다. [^source35]

### 15.2 추가·축소 우선순위

데이터 준비 상태 점검은 첫 흐름에 포함한다. 정정 공지의 변경 전후 비교는 추가 가치가 있는 후보로 두고, 초기 핵심 흐름을 완성한 뒤 범위를 판단한다.

모의 회수는 고객이 정기 훈련에 가치를 느끼는지 확인한 뒤 검토한다. 세트상품 추적은 실제 투입 제조분 기록이 있어야 하며 후순위다. [^source37]

라벨 이미지 분석, 여러 명세서 형식, 복잡한 세트 구성, 자유로운 자연어 질문, 고급 보고서 디자인은 일정이 부족하면 축소한다. 실제 ERP·쇼핑몰 연동, 외부 판매중지 실행, 메시지 자동 발송은 후속 단계다. [^source38]

## 16. 고객·데이터·효과 검증 계획

### 16.1 고객 문제: 최근 사건 한 건을 재현한다

초기 목표는 서로 다른 업체의 품질·물류 등 담당자 3~5명과 최근 업무 사례를 확인하는 것이다. 작은 표본이므로 시장 전체를 입증하는 조사로 표현하지 않는다.

| 확인할 질문 | 필요한 이유 |
| --- | --- |
| 최근 회수 요청을 어디서 어떤 형식으로 받았는가 | 실제 업무 시작점을 확인 |
| 어떤 시스템·문서를 열었는가 | 기존 해결 수단을 파악 |
| 상품·제조분·출고를 어떤 순서로 찾았는가 | 업무 단계를 재현 |
| 무엇을 다른 부서나 물류사에 요청했는가 | 추가 확인의 원인을 파악 |
| 직접 작업한 시간과 회신을 기다린 시간은 얼마인가 | AI로 줄일 수 있는 시간과 외부 대기를 분리 |
| 기존 시스템의 기능 부족인가, 사용 절차의 불편인가 | 문제 성격을 구분 |
| 파일 제공·연동이 가능한가, 누가 예산을 결정하는가 | 도입 조건을 확인 |

문서 비교가 느린 것과 기록 자체가 없거나 외부 회신이 늦은 것은 다르다. 후자는 AI 문서 분석만으로 해결되지 않는다. [^source39]

### 16.2 데이터 확보: 실제 연결을 검사한다

익명화한 상품·입고·재고·출고 자료와 명세서로 필드와 연결 관계를 확인한다. 상품이 같은지, 사건에 필요한 날짜·제조번호가 있는지, 특정 입고와 출고·주문을 실제로 연결할 수 있는지를 점검한다.

화면 설명으로 구조만 확인한 경우, 실제 파일을 받아 연동한 경우, 합성 데이터로 재현한 경우를 구분해 기록한다. 지원 범위는 확인된 연결 수준에 맞춰 제한한다. [^source40]

### 16.3 효과 검증: 세 방식을 비교한다

| 비교 방식 | 측정 목적 |
| --- | --- |
| 담당자의 기존 문서·스프레드시트 처리 | 현재 업무 수준 |
| 식별자·키워드·날짜·단위 규칙 기반 도구 | 기본 자동화가 주는 효과 |
| 규칙 기반 도구 + AI | AI가 추가로 주는 효과 |

전체 제품 전에 **문서 입력 → 조건 추출 → 상품 후보 → 기록 대조 → 담당자 확인**만 구현해 실험을 시작할 수 있다.

파일 준비부터 최종 확인까지의 시간을 측정하고, 정답은 실험 전에 원문·원장을 대조해 만든다. 같은 사람이 같은 사건의 답을 외우는 영향을 줄이도록 사례와 수행 순서를 나눈다.

통과 기준도 실험 전에 정한다. 예를 들어 중요한 오류가 늘지 않으면서 총 검토시간이 줄어드는지를 볼 수 있다. 목표 개선율은 아직 정해지지 않았다. 팀원과 합성 자료만으로 측정했다면 “가상 업무 시나리오에서의 비교”라고 발표한다. [^source41]

## 17. 평가 데이터와 지표

### 17.1 평가 사례

공개 회수 공지와 가상 기업 데이터를 결합하고, 각 기록의 정답 판정을 사람이 먼저 작성한다. 다음 난점을 포함한다.

| 범주 | 포함할 사례 |
| --- | --- |
| 식별 | 정확한 상품번호, 축약·변형 상품명, 유사 이름의 다른 제조사 |
| 대상 조건 | 다른 규격·제조번호, 날짜 범위 경계, 행별 조건 관계 |
| 추적 | 부분 출고, 제조분·주문 연결 누락 |
| 증거 | 제조번호 누락, 문서·DB 충돌, 추가 자료로 일부만 해결 |
| 후속 범위 | 세트 구성 기록을 구현한 경우 해당 추적 사례 |

세트는 초기 필수에서 제외했으므로 첫 버전에서 구현하지 않으면 첫 평가의 필수 항목으로 약속하지 않는다. 원문의 평가 후보를 후속 범위 조정에 맞춰 구분한 것이다. [^source42]

### 17.2 측정 지표

| 영역 | 지표 |
| --- | --- |
| 조건 해석 | 항목·논리 관계와 최종 대상 집합의 정확성 |
| 후보 검색 | 정답 상품 후보 포함률, 놓친 후보 비율 |
| 상품 연결 | 올바른 연결·잘못된 연결 비율 |
| 대상 판정 | 대상 누락, 비대상 오탐, 잘못된 비대상 확정 |
| 불확실성 | 확인 필요 비율, 정보 부족인데 잘못 확정한 비율 |
| 증거 보완 | 추가 자료로 실제 해결된 비율, 수정 횟수 |
| 영향 추적 | 정답 재고·주문·수량과의 일치 |
| 근거 | 인용한 원문이 결론을 실제로 뒷받침하는지 |
| 운영 | 처리시간, API 비용, 분석 실패율 |
| 업무 효과 | 파일 준비부터 최종 확인까지의 총 작업시간 |

전부 확인 필요로 남기면 오판은 줄어도 유용성이 낮아진다. **정확도, 보류율, 검토시간을 함께 평가한다.** 아직 측정하지 않은 성능 수치는 넣지 않는다. [^source43]

## 18. 대회 시연 시나리오

가상 기업 데이터임을 표시하고 다음 흐름을 한 사건으로 보여준다.

| 순서 | 시연 장면 | 보여줄 점 |

| 4 | 비슷하지만 규격이 다른 후보 제외 | 오연결 방지 |
| 5 | 필요한 제조분 정보가 있는 기록 판정 | 조건에 맞는 대상 확인 |

| 11 | 미처리·미확인·근거가 남은 내부 결과표 출력 | 완료와 미완료를 투명하게 표시 |

초안의 재고 120개·출고 주문 34건은 가상 예시이며 실적이나 확정된 시연 수치가 아니다. 실제 시연 수량은 데이터와 정답표를 만든 뒤 맞춰야 한다.

시연의 핵심은 “AI가 전부 맞혔다”가 아니라 **정확한 연결, 잘못된 연결 거절, 정보 부족 표시, 증거에 따른 제한적인 결과 변경**이다. [^source44]

### 21.2 첫 버전 완료 기준

샘플 데이터로 바로 체험할 수 있고, 원문 근거와 상품 후보를 검토할 수 있어야 한다. 대상·비대상·확인 필요가 분리되어야 하며 기록에 근거한 재고·출고 범위를 조회할 수 있어야 한다.

추가 증거에 따른 판정 변경, 담당자 확인·작업 이력, 정답 데이터 기반 평가까지 이어지는 것이 목표다. 전체 서비스를 넓게 만드는 것보다 이 핵심 흐름을 연결하는 것이 우선이다. [^source48]

## 22. 남은 결정과 지금 할 일

| 남은 결정 | 확인할 내용 | 결과에 따른 선택 |
| --- | --- | --- |
| 고객 문제 | 실제로 오래 걸리는 단계는 무엇인가 | 반복되는 병목에 집중 |
| 데이터 | 제조분부터 어디까지 연결 가능한가 | 지원 범위를 기록이 있는 지점으로 제한 |
| AI 효과 | 기본 검색·규칙보다 검토를 개선하는가 | 효과가 없는 AI 사용은 축소 |
| 차별성 | 기존 도구로 해결되지 않는 부분이 있는가 | 고객군·문제·기능 범위 조정 |
| 팀 여건 | 인원·역량·기간에 맞는가 | 문서 형식·세트·부가기능 축소 |

상품 대조만 불편하면 매칭·검토 중심으로 좁힌다. 기존 시스템이 충분하면 고객군이나 문제를 바꾼다. 기록이 없으면 AI가 해결한다고 주장하는 대신 정밀 추적의 전제를 재검토한다. [^source49]

지금의 실행 순서는 다음과 같다.

**최근 회수 사건 한 건 확인 → 필요한 자료와 연결 관계 점검 → 정답표 작성 → 가장 오래 걸리는 대조 단계 구현 → 기존 방식·규칙 기반·AI 비교 → 효과가 확인된 범위만 유지.**

현재 기획의 정확한 상태는 **“검증 가능한 서비스 가설이며, 실제 고객의 사건과 데이터로 성립 여부를 확인해야 한다”**이다. [^source50]

## 23. 팀 공유용 최종 소개문

> **WeCall B2B는 포장 가공식품 유통사가 회수 통보를 받은 이후 수행하는 대상 확인과 대응 업무를 지원하는 AI 서비스입니다. 회수 문서의 상품·대상 조건을 내부 상품 및 입출고 기록과 대조하고, 기록으로 확인되는 재고·출고 영향과 추가 확인이 필요한 항목을 구분합니다. AI는 문서 해석과 상품 후보 비교를 보조하고, 조건 비교·수량 계산·추적은 코드와 DB로 처리합니다. 담당자는 근거를 검토해 조치를 승인하고 처리 증빙을 관리합니다. 초기에는 한 기업의 제한된 데이터와 문서 형식으로 검증하며, 고객 수요와 데이터 확보 가능성, 기존 방식 대비 효과는 별도 검증 과제입니다.**

핵심 방향은 **“리콜 알림”이 아니라 “회수 통보 이후의 근거 기반 대조·판별·대응 관리”**다.
