# 사건 종료 점검·승인·재개

## 의미와 범위

종료는 제품 안의 **내부 업무 종료**다. 실제 물리적 회수 완료나 법적 의무 충족을 자동 판단하지 않는다.
검토자는 [로그인한 REVIEWER 계정](auth-api.md)을 사용한다. 대상 범위와 조치·증빙의 충분성은 사람이 최종 검토한다.
확인 필요 판정을 강제로 비대상이나 완료로 바꾸는 예외 종료는 제공하지 않는다.

## API

기본 경로: `/api/v1/recalls/{caseId}`.

| 메서드·경로 | 동작 |
| --- | --- |
| GET /closure-check?assessmentId={runId} | 종료 가능 여부·차단·주의 항목·검토 대상 목록 |
| POST /closure | 점검 재실행 후 종료 승인 |
| POST /reopen | 사유를 기록하고 재개 |
| GET /lifecycle | 현재 상태와 종료·재개 이력·종료 당시 점검 스냅샷 |

기존 GET /{caseId}에도 status(OPEN/CLOSED), lifecycleVersion, closedAt을 추가했다.
점검 시 assessmentId를 생략하면 NO_ASSESSMENT 등 준비 상태를 볼 수 있다. 다른 사건의 판정은 404다.

종료 요청:

```json
{
  "assessmentId": "00000000-0000-0000-0000-000000000000",
  "expectedVersion": 0,
  "reviewer": "local-reviewer",
  "note": "현재 대상 범위와 조치·취소 사유·증빙을 검토함",
  "responseCoverageConfirmed": true
}
```

판정 UUID는 실제 값으로 대체한다. expectedVersion은 점검 응답의 version 또는 사건 응답의 lifecycleVersion이다.
이는 **종료·재개 횟수 버전**이며 작업 version과 다르다. 종료 승인 시 작업 등 최신 상태를 잠금 아래 다시 점검하므로 이전 점검의 ready만 믿고 처리하지 않는다.
reviewer는 로그인 계정을 사용하므로 생략 가능하고 note는 2000자 이하의 공백 아닌 문자열이 필요하다. responseCoverageConfirmed가 false/누락이면 400이다.

재개 요청: `{"expectedVersion":1,"reviewer":"local-reviewer","note":"정정 통보 도착으로 재검토"}`.
종료 상태에서만 재개 가능하며 새 종료·재개마다 lifecycleVersion이 1 증가한다.

## 차단 항목

| 코드 | 차단 이유 |
| --- | --- |
| CASE_CLOSED | 이미 종료됨 |
| NO_CONDITION | 회수 조건이 없음 |
| PENDING_CONDITIONS | 미승인 조건 버전이 있음 |
| NO_ASSESSMENT | 종료 기준 판정 미지정 |
| OUTDATED_ASSESSMENT | 가장 최근 조건 버전의 판정이 아님 |
| UNRESOLVED_RECEIPTS | 확인 필요 입고가 있음 (count: 입고 건수) |
| UNRESOLVED_SHIPMENTS | 확인 필요 출고가 있음 (count: EA 수량) |
| INCOMPLETE_TASKS | OPEN/IN_PROGRESS 작업이 있음 |
| NO_COMPLETED_RESPONSE | 대상 재고·출고가 있지만 완료한 대응 작업이 없음 |
| PENDING_RECEIPT_EVIDENCE | 미검토 입고 증거가 있음 |
| PENDING_TASK_PROOFS | 취소된 작업을 포함해 미검토 처리 증빙이 있음 |

모든 초안 조건을 검토해야 한다. 조건 초안 폐기 API는 아직 없다. 같은 조건으로 재실행한 판정은 입력·조건이 같으므로 선택 가능하지만, 이전 조건 버전으로 종료하지는 못한다.
취소된 작업은 완료로 세지 않는다. 취소 작업의 미검토 증빙도 정리할 수 있도록 **기존 작업 증빙 검토 API를 CANCELLED 상태에도 허용**했다. 증빙 검토는 취소 상태를 되돌리거나 작업을 완료하지 않는다.

차단되면 409 CLOSURE_BLOCKED와 check 전체를 반환한다. 승인·종료 이력은 생성하지 않는다.
잘못된 상태 전이·버전은 409, 없는 사건은 404다.

## 사람이 확인해야 하는 항목

점검의 warnings는 취소된 작업, 다른 판정에 연결된 작업, 판정에 연결되지 않은 사건 단위 작업을 표시한다.
ready는 기계적 차단 항목이 없다는 의미이며 자동 종료 승인이 아니다.
현재 시스템은 작업 지시·처리 수량을 구조화된 원장으로 관리하지 않으므로 **각 대상에 필요한 모든 조치가 충분히 이루어졌는지**를 자동 증명하지 않는다. 종료 검토자는 responseCoverageConfirmed로 현재 범위에 대한 작업·취소 사유의 적합성을 확인하고 note에 기록한다.
다른 판정의 완료 작업은 자동 폐기하지 않는다. 부족하면 사건이 열린 상태에서 작업을 재개하거나 새 작업을 등록해야 한다.

## 상태 보존과 동시성

종료 승인·재개는 case_lifecycle_event에 검토자·사유·시각·버전을 추가한다. 종료 이벤트는 기준 판정, 당시 점검 결과, 작업 ID·버전·상태, 증거·증빙 검토 상태를 JSONB로 보존한다.
재개 후에도 이전 스냅샷은 바뀌지 않는다. 종료 실패 시 상태와 이력을 함께 롤백한다.

종료 상태에서는 새 조건, 조건 승인·판정 실행, 입고 증거 등록·승인·거절, 작업 생성·배정·전이·증빙 등록·검토를 모두 차단한다. 조회는 가능하다. 관계없는 기업 데이터 CSV 업로드는 가능하지만 종료 사건에 적용할 수는 없다.
재개는 기존 판정·작업을 자동 변경하지 않는다. 새 자료에 따라 재판정하고 필요한 작업을 재개해야 한다.

모든 사건 변경 API는 사건 행 → 조건/증거/작업 순서로 잠근다. 종료 점검 도중 새 작업이 끼어들어 종료 조건을 우회하지 못한다.
API 외부에서 DB를 직접 수정하는 경로는 지원하지 않는다.

## 시연

백엔드 실행 후 저장소 루트에서:

```sh
python3 scripts/demo_closure.py
```

첫 사건은 기존 샘플을 그대로 사용하여 증거 보완·작업 완료 후에도 미연결 출고 10개가 남아 종료가 차단됨을 확인한다.
두 번째 사건은 **별도 가상 데이터(제조분이 알려진 재고 5개, 출고 없음)**로 종료 → 변경 차단 → 재개 → 재종료를 시연한다. 원래 샘플의 미연결 기록을 추정해 채우지 않는다.

전체 52개 테스트 중 종료 통합 테스트 11개로 차단 항목·이력 보존·기존 API 보호·동시 승인/작업 생성·감사 이력 롤백을 검증했다. 종료 성공 테스트는 명시적인 입고·출고 연결을 가진 별도 합성 데이터를 사용한다.
