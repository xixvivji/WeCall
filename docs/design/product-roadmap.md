# 기능 보완 설계와 완성도 기준

기준일: 2026-09-17. BACKLOG-01은 2026-09-18 구현 완료했으며 나머지 BACKLOG 항목은 미구현 제안이다. 현재 기능은 [MVP 요구사항](../mvp-requirements.md)에 구분한다. OCR 보류·로컬 문서 처리·develop 통합·배포 보류는 사용자의 기존 방향을 유지한다. 새 일정·개발 착수·외부 연동을 확정하는 문서는 아니다.

## 우선순위를 정하는 기준

기능 개수보다 “담당자가 어떤 근거로 무엇을 결정했고, 다음에 무엇을 확인해야 하는지 설명할 수 있는가”를 먼저 본다. 누락을 숨기거나 서로 다른 버전을 혼합할 수 있는 지점을 먼저 보완하고, 실제 사용 자료와 관찰로 필요한 범위를 조정한다.

| 우선순위 | ID | 보완안 | 필요한 이유 | 상태 |
| --- | --- | --- | --- | --- |
| P0 | BACKLOG-01 | 원문 변경 후 재검토 관리 | 원문 수정 뒤 과거 조건·판정을 최신 근거로 오해하지 않도록 관리 | 구현 / [재검토 계약](source-revalidation.md) |
| P0 | BACKLOG-02 | 분석 실패 원인·해결 안내 | 입력 초과·지원하지 않는 문장·서버 장애를 사용자가 구별하기 어려움 | 설계 제안 |
| P0 | BACKLOG-03 | 대표 문서 인수 검증 | 합성 정답 일치와 현업 사용 가능성은 다름 | 자료·검토자 필요 |
| P1 | BACKLOG-04 | 작업 기한·우선순위·지연 목록 | 담당자·상태는 있으나 무엇을 먼저 처리할지 관리하는 정보가 부족함 | 설계 제안 |
| P1 | BACKLOG-05 | 상품 후보 비교 지원 | 내부 상품 연결은 현재 사람의 수동 검토이며 원 기획의 후보 추천은 미구현 | 자료 검증 후 제안 |
| 조건부 | BACKLOG-06 | 긴 문서의 분석 범위 선택 | 실제 문서가 현재 입력 한도를 반복적으로 넘으면 필요 | 빈도 측정 후 결정 |
| 운영 전 | BACKLOG-07 | 검사 엔진·복구·접근 검증 | 로컬 기능 검증만으로 회사 자료 운용 준비를 대신할 수 없음 | 배포 재개 시 진행 |

BACKLOG-01 구현 후 권장 다음 구현은 BACKLOG-02다. BACKLOG-03은 사용할 수 있는 자료를 확보하는 대로 병행한다. P1은 MVP 데모를 막는 필수 조건으로 넣지 않는다.

## BACKLOG-01: 원문 변경 후 재검토 관리

**사례:** v1로 조건 승인·판정을 마친 뒤 공문 정정으로 원문 v2를 저장하면, 과거 판정은 v1 근거의 기록으로 남아야 한다. 사용자는 이를 v2 검토까지 끝난 결과로 오해하지 않아야 한다.

2026-09-18 구현: 조건·판정의 원문 버전, 영향 없음 검토, 초안 철회, 승인·판정·증거 보완·종료 차단과 화면 표시를 추가했다. [실제 동작과 이관](source-revalidation.md)을 따른다. 아래는 기능의 설계 기준이며 조건의 기준 원문이 불명확한 과거 기록은 NULL로 보존한다.

제안:

- 조건을 만들 때 기준 원문 버전을 기록한다. AI 전환·수동 작성·증거 보완으로 파생되는 조건 모두 기준을 정의한다.
- 원문 수정 시 기존 조건·판정을 삭제하지 않고 ‘이전 원문 기준 / 재검토 필요’로 구분한다. 대시보드·다음 할 일·보고서에서 같은 기준을 사용한다.
- 담당자가 새 원문 기준으로 조건을 재작성·승인하거나, 영향 없음의 근거를 남겨 재검토를 해소한다. 영향 없음 확인은 과거 승인 기록을 덮어쓰지 않는다.
- 해결되지 않은 재검토 항목이 있으면 종료 점검에서 표시하고 종료를 차단하는 방안을 적용한다. 실제 종료 기준은 이 기능 구현 때 기존 정책과 함께 확정한다.
- 기존 조건의 기준 원문 버전을 확실히 복원할 수 없으면 ‘기록 없음’으로 남긴다. 단순히 최신 원문에 연결하지 않는다.

완료 기준: v1 판정 → v2 수정 → 재검토 표시 → 검토 해소 → 종료 점검의 전체 흐름을 검증한다. 과거 수량·승인·근거는 바뀌지 않고, 동시 수정 충돌과 v1 내용으로 복원하는 경우도 새 버전으로 취급한다. 관련 문서: [원문 이력](source-pdf.md), [종료 점검](closure-api.md).

## BACKLOG-02: 분석 실패 원인·해결 안내

현재: FastAPI는 입력 제한·수동 검토·모델 장애를 구분하지만 Spring의 오류 매핑은 일부를 합쳐 보여준다. UI에는 고정 입력 한도 안내와 재시도가 있다.

제안: 원문 입력 화면에서 UTF-8 바이트·줄 수와 분석 가능 여부를 보여준다. 서버 오류는 최소한 ‘입력 한도 초과 / 지원하지 않는 조건 / 응답 검증 실패 / 모델 사용 중 / 연결·시간 초과’로 구분하고 각 경우에 맞는 수동 작성·대기·재시도 경로를 제공한다. 사용자에게 문서 본문이나 내부 서버 오류를 노출하지 않는다. 프론트 검사와 별도로 서버 한도 검사는 유지한다.

완료 기준: 한글·이모지 등에서 글자 수와 바이트 수를 혼동하지 않는다. 실패해도 원문·수정 내용이 유지되고, 반복 클릭으로 같은 사건의 분석을 중복 생성하지 않는다. 외부 모델로 자동 대체하지 않는다.

## BACKLOG-03: 대표 문서 인수 검증

첫 검증 묶음은 명확한 단일 조건, AND/OR, 소비기한 범위, 상품명이 비슷하지만 규격이 다른 경우, 문서 정정, 제조번호 누락, 출고 연결 누락, 추출 불가능한 문서, 긴 문서로 구성한다. 실제 회사 자료는 사용 허용 범위와 정답 검토자를 먼저 확인하고 저장소에는 넣지 않는다. 자료가 없으면 합성 사례로 흐름을 검증하되 현업 인수로 보고하지 않는다.

| 측정 항목 | 기록할 값 | 완료·보류 판단 |
| --- | --- | --- |
| 조건 추출 | 정확 추출·잘못된 조건·안전한 거절·과도한 거절·실행 오류 | 분모와 문서 유형을 공개하고 잘못된 조건 사례의 처리 상태를 남김 |
| 사람이 확인하는 과정 | 조건 누락 발견, 수정 횟수, 검토 시간, 도움 없이 완료 여부 | 수동 기준과 같은 사례로 비교; 개선율을 미리 성과로 단정하지 않음 |
| 판정·수량 | 정답표 대비 대상 집합·재고·출고·연결 미확인 수량 | 검증용 정답표와 정확히 일치, 미연결 수량을 임의 배분하지 않음 |
| 장애·회복 | 모델 꺼짐, 저장 실패, 동시 수정, 다운로드 실패 | 입력·과거 기록 보존, 오류 설명, 재시도와 중복 방지 확인 |
| 업무 적합성 | 실제 담당자의 미완료 항목·수정 요청·인수 여부 | 남은 이슈와 수락 기준을 기록하고 담당자가 인수 여부 결정 |

합성 35건의 최종 추출·거절 기대 일치는 모델 단독 정확도나 실제 문서 정확도가 아니다. 기존 개발 사례·확장 사례·보류 평가 사례를 구분한 [평가 결과](../validation/ai-evaluation-expansion-2026-09-16.md)를 유지한다. 실무 성공률·시간 목표는 기준 측정과 담당자 합의 후 정한다.

## BACKLOG-04: 작업 기한과 우선순위

제안 필드: 선택적 `dueAt`, 우선순위, 변경 사유. 기한·우선순위 변경 이력과 버전 충돌을 기록하고 내 할 일에서 기한 임박·기한 초과를 필터링한다. 임박 기준과 표시 시간대는 구현 전에 정한다. 기존 작업은 기한 미지정으로 이전한다.

완료 기준: 날짜 경계·완료·취소·재개 시 표시가 일관되고, 기한 초과가 자동으로 작업 상태를 바꾸지 않는다. 담당자 이외 실행 제한은 유지한다. 외부 메일·문자·고객 발송은 이 기능에 포함하지 않는다.

## BACKLOG-05: 상품 후보 비교 지원

현재 상품 연결은 사람이 데이터 버전·상품을 선택하고 근거를 기록한다. AI 상품 자동 매칭은 없다.

제안: 먼저 현재 CSV의 상품명·제조사·규격으로 후보를 검색하고 각 속성의 일치·불일치·누락을 나란히 표시한다. 실제 데이터가 지원하지 않는 바코드·ERP 식별자를 있다고 가정하지 않는다. 임베딩이나 추가 모델은 단순 검색의 한계를 측정한 후 검토한다.

완료 기준: 같은 이름·다른 규격, 제조사 누락, 후보 없음·여러 후보를 구별한다. 후보 순위가 대상 확정으로 이어지지 않으며 사람이 이유를 남겨 연결한다. 후보에서 빠진 상품을 검색·선택하는 경로도 제공한다.

## BACKLOG-06: 긴 문서 처리

현재 한도는 6,000바이트·80줄이다. PDF 추출 성공과 AI 입력 가능 여부는 별개다. 우선 실제 입력 중 한도 초과 비율을 측정한다.

필요하면 전체 원문을 보존한 채 사람이 분석할 구간을 선택하고, 선택 구간과 원문 버전·위치를 분석 이력에 남긴다. 결과가 문서 전체를 분석한 것처럼 표시하지 않는다. 예외·정정 문구가 선택 범위 밖에 있을 수 있음을 검토하게 한다. 문서 분할·상품별 규칙 결합의 자동화는 단순 구간 선택과 별도 작업으로 평가한다. 조용히 잘라 읽는 방식은 사용하지 않는다.

## BACKLOG-07: 운영 준비

배포 보류를 해제할 때 저장 위치·접근 범위·보관 정책을 정하고, 실제 악성 파일 엔진, DB와 파일의 함께 복원, 시크릿·로그·HTTPS·모니터링, 모델 자원 제한을 검증한다. 운영 구성과 방화벽은 로컬 모델 연결만으로 완료되지 않는다. 담당자·환경·복구 목표는 아직 미정이다. [파일 관리](file-data-policy.md)

## 완성도 단계

| 단계 | 현재 판단 | 다음 단계로 넘어갈 근거 |
| --- | --- | --- |
| 개발 MVP | 주요 흐름 구현·합성 검증 완료, 알려진 한계 있음 | 현재 기능과 제한을 설명하고 반복 시연 가능 |
| 인수 가능한 MVP | 검증 대기 | P0 보완 검토, 대표 자료 정답·예외 흐름 확인, 담당자 인수와 잔여 이슈 기록 |
| 운영 준비 | 미완료·배포 보류 | 승인된 운영 환경, 복원·접근·검사·장애 대응 검증 |

기능 테스트 수를 제품 완료율로 환산하지 않는다. OCR, ERP·메일 연동, 자동 외부 조치, 실제 회수 수량 원장, 다중 기업 기능은 별도 요구가 확인될 때 다시 범위를 정한다.
