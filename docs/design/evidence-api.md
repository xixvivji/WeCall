# 입고 증거 보완·재판정 API

## 구현 범위

입고명세서 텍스트와 검토자가 읽은 값을 등록하고, 특정 **기존 판정의 입고 건**에 연결한다. 일치 여부와 충돌을 확인한 뒤 승인하면 새 데이터 버전·조건 버전·판정이 한 트랜잭션으로 생성된다.

지원하는 보완은 **누락된 제조번호·소비기한 채우기**다. 이미 존재하는 다른 값을 덮어쓰거나 입고량을 변경하지 않는다. 혼합 제조분·부분 수량 문서·기존 값 정정은 이번 자동 보완 범위에서 제외한다.
현재 입력은 JSON의 documentText로 전달하는 텍스트다. PDF/이미지 업로드, OCR, AI 추출, 파일 저장소는 아직 연결하지 않았다.
승인자는 [로그인한 검토자 계정](auth-api.md)으로 기록한다.

## 요청과 응답

기본 경로: `/api/v1/recalls/{caseId}/evidence`.

| 메서드·경로 | 설명 |
| --- | --- |
| POST 기본 경로 | 문서·보완 제안 등록 (201, PENDING) |
| GET /{evidenceId} | 원문·해시·보완 전후·검토 항목·상태·승인/거절 이력 조회 |
| POST /{evidenceId}/approval | 누락값 보완과 재판정 (200) |
| POST /{evidenceId}/rejection | 사유를 기록하고 거절 (200) |

등록 요청은 [샘플 JSON](../../samples/recall-001/evidence-request.json)을 사용한다. baseAssessmentId의 0 UUID는 실제 기존 판정 UUID로 대체한다.

- baseAssessmentId: 같은 사건의 기존 판정. 데이터 버전과 회수 조건을 고정한다.
- receiptId: 그 판정의 데이터에 존재하는 입고 ID.
- documentText / sourceQuote: 문서 원문(최대 100000자)과 인용(최대 10000자).
- observedProductId / observedReceivedQuantity / observedReceivedAt: 문서에서 확인한 상품 ID·전체 입고 수량·입고일. 기존 입고 기록과 대조한다.
- lotNumber / expiryDate: 보완 제안. 최소 하나 필요하고 사용하지 않는 필드는 null 또는 생략한다. 제조번호는 500자 이하의 앞뒤 공백 없는 값, 날짜는 ISO 날짜다.

등록만으로 데이터는 바뀌지 않는다. 존재하지 않는 사건·판정·입고는 404, 필수값·형식 오류는 400이다.
기존 기록과 불일치하거나 원문 근거가 부족한 자료도 **PENDING으로 보존**하고 issues로 표시한다.
SHA-256은 입력 텍스트의 UTF-8 바이트에 대한 해시이며 외부 문서의 진위 증명은 아니다.

승인 요청:

```json
{
  "reviewer": "local-reviewer",
  "note": "입고 건·상품·날짜·전체 수량과 단일 제조분 확인",
  "receiptAndSingleLotConfirmed": true
}
```

검토자는 명세서가 해당 입고 **전체 수량의 단일 제조분**을 증명하는지 확인해야 한다. 확인값이 false이거나 누락되면 400이다. reviewer는 로그인 계정으로 대체되므로 생략 가능하다. note는 2000자 이하의 공백 아닌 문자열이다.
코드는 원문 인용 포함 여부와 제안 값의 인용 포함 여부를 검사하지만 문장의 의미·표의 관계·문서 진위까지 검증하지 않는다. 단순 문자열 포함 검사가 사람의 검토를 대신하지 않는다.

거절 요청: `{"reviewer":"local-reviewer","note":"혼합 제조분 자료로 확인됨"}`.
거절은 데이터 버전·판정을 생성하지 않으며 원문과 사유를 보존한다. 검토 완료 자료를 수정하거나 재승인하는 API는 없다. 수정 자료는 새 증거로 등록한다.

## 승인 차단 항목

409 EVIDENCE_BLOCKED의 issues에는 field, code, message가 들어간다.

| 코드 | 의미 |
| --- | --- |
| PRODUCT_MISMATCH | 문서와 입고 상품 불일치 |
| QUANTITY_MISMATCH | 전체 입고량 불일치. 부분 수량은 자동 확대하지 않음 |
| DATE_MISMATCH | 입고일 불일치 |
| QUOTE_NOT_FOUND | 인용문이 원문에 없음 |
| VALUE_NOT_IN_QUOTE | 제안 제조번호/소비기한이 인용에 없음 |
| EXISTING_VALUE_CONFLICT | 현재 존재하는 값과 제안이 충돌 |
| NO_MISSING_VALUE_TO_FILL | 채울 누락값이 없음 |

PENDING 상태만 승인·거절할 수 있다. 이미 처리한 자료는 409이며 중복 승인과 승인·거절 경합에서도 한 번만 적용한다.

## 버전 보존과 추적 경계

승인하면:

1. 기준 판정의 데이터 스냅샷을 복제한다. asOf는 원래 재고·출고 기준 시각을 유지한다.
2. 해당 입고의 NULL인 제조번호/소비기한만 채운다.
3. 기준 판정의 회수 조건·상품 검토를 그대로 복사한 새 조건 버전을 같은 검토자 계정으로 승인한다. 이 승인은 **동일 조건을 보완된 데이터에 재적용하는 것까지 포함**한다.
4. 새 판정을 저장하고 증거에 결과 데이터·판정 ID, 승인자·메모·시각을 기록한다.

중간 단계 실패는 데이터 복제·조건·판정·승인 모두 롤백한다. 원본 문서·데이터·기존 판정은 유지한다.
출고 연결 행은 그대로 복사하며, 입고 증거로 새로운 출고 연결을 만들지 않는다. 따라서 S2 미연결 10개는 계속 확인 필요다.
승인 응답의 resultAssessmentId를 [기존 판정 조회 API](recall-api.md)에서 조회한다. 증거 조회는 before/after 입고 사실과 두 결과를 연결할 ID를 제공한다.

baseAssessmentId가 명시적 기준이므로 이후 자료는 **직전 보완 결과 판정 ID**를 기준으로 등록해야 보완 내용이 누적된다. 이전 판정을 지정하면 별도 분기 결과를 만들며, 다른 분기의 보완을 자동 합치거나 최신 결과를 자동 선택하지 않는다.
현재 구현은 불변 데이터 전체 복제로 단순성을 유지한다. 대용량에서 변경분 저장으로 전환할 수 있으나 이 단계에서는 도입하지 않았다.

## 시연·검증

백엔드 실행 후 저장소 루트에서:

```sh
python3 scripts/demo_recall.py --with-evidence
```

스크립트는 새 합성 사건을 생성하고 사전 작성한 가상 증거를 demo-reviewer 계정으로 승인한다. 실제 담당자의 검토를 완료했다는 의미는 아니다.

| 지표 | 승인 전 | 승인 후 |
| --- | ---: | ---: |
| 대상 재고 | 110 | 140 |
| 확인 필요 재고 | 30 | 0 |
| 대상 출고 | 60 | 70 |
| 확인 필요 출고 | 20 | 10 |

샘플 정답표의 after 결과와 입고별·출고별 결과를 비교하고, 기존 판정 보존, 충돌·부분 수량 차단, 확인 미완료 차단, 거절, 동시 승인, DB 실패 롤백을 PostgreSQL 통합 테스트로 확인한다.
