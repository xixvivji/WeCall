# WeCall B2B 프로젝트 개요

## 목적과 사용자

국내 포장 가공식품 유통사가 회수 통보를 받은 뒤, 외부 문서와 내부 상품·입출고 기록을 대조하여 대상과 영향 범위를 확인하고 담당자 조치·증빙을 관리하는 서비스다. 주 사용자는 품질·상품관리 담당자이며 첫 버전은 한 기업과 검토자·실행 담당자 두 역할을 기준으로 한다.

고객 수요와 개선 효과는 아직 검증 전 가설이다. 아래 기능은 구현 목표이며 현재 구현 완료 상태가 아니다.

## 첫 버전의 흐름

기업 CSV 등록 → 사건 등록 → 회수 조건 추출·검토 → 내부 상품 연결 → 대상 판정·영향 조회 → 추가 증거 검토 → 작업·증빙 기록 → 내부 종료 승인.

- 입력: 정해진 양식의 상품·입고·재고·출고 CSV, 붙여넣은 회수 본문, 입고명세서 한 종류.
- 출력: 원문 근거, 상품 후보, 대상·비대상·확인 필요, 실제 기록으로 연결된 재고·출고 범위, 미확인 항목, 작업 이력.
- 초기 제외: ERP·이메일 자동 연동, 외부 판매중지 실행, 고객 자동 발송, 복잡한 세트 추적.

## 반드시 유지할 설계 원칙

- AI는 조건·정보 추출과 상품 후보 비교의 초안을 제공한다. 담당자가 검토·승인한다.
- 승인된 조건 비교, 수량 계산, 기록 추적은 Java·DB가 처리한다.
- 정보 누락·충돌은 비대상이 아니라 확인 필요로 남긴다.
- 상품 연결 상태, 회수 대상 여부, 작업 상태는 각각 관리한다.
- 실제 연결 기록이 없는 제조분·출고·주문 관계를 추정하여 확정하지 않는다.
- 원문, 추출값, 수정·승인 이력, 판정 버전과 분석 모델·프롬프트 버전을 보존하도록 설계한다.

## 기술과 현재 상태

| 구분 | 구성 및 상태 |
| --- | --- |
| 백엔드 | Java 21 · Spring Boot 3.5.16 · Gradle 8.7 기초 구성 완료 |
| AI 서버 | Python 3.12 · FastAPI · uv 기초 구성 완료 |
| 검증 | 서버별 상태 API 테스트, 백엔드 빌드 확인 |
| DB·등록 API | PostgreSQL · Flyway · JDBC, CSV 5종 일괄 검증·등록 구현 |
| 회수 API | 사건·조건 버전 등록·수동 승인, 대상 판정·영향 결과 보존 구현 |
| 미구현 | 인증·권한, 증거 보완·작업·종료, AI 분석, 서버 간 호출 |
| 미결정 | 프론트, AI 모델·OCR·임베딩, 저장소, 배포 환경 |

Spring Boot가 업무 데이터와 승인을 관리하고 FastAPI가 AI 분석 결과·근거를 반환하는 구조를 계획한다.

## 개발 시작 순서 (제안)

1. **샘플 사건 1건과 정답표:** 가상 상품·입고·재고·출고 자료에 대상, 비대상, 정보 누락, 출고 연결 누락 사례를 넣는다. 각 결과의 근거와 기대 수량을 작성한다.
2. **DB 선택·ERD·CSV 계약:** 상품, 입고 제조분, 재고, 출고, 사건, 조건 버전, 판정, 증거, 작업의 키와 연결 관계를 정의한다. PostgreSQL로 확정했다.
3. **첫 업무 흐름:** CSV 검증·등록 → 사건·수동 조건 등록 → 조건 승인 → 판정 → 영향 조회를 구현한다. 정답표로 대상 집합과 수량을 검증한다.
4. **AI 연동 계약·구현:** 요청 ID, 입력 문서, 구조화된 조건·근거, 실패 응답을 합의한다. FastAPI 분석 결과는 승인 전 초안으로 저장한다.
5. **증거·작업·종료:** 증거 승인과 재판정, 담당자 작업·증빙, 미확인·미처리 항목 확인과 종료 승인을 연결한다.

첫 개발 목표는 샘플 사건 하나에서 승인된 조건을 적용해 대상·비대상·확인 필요와 추적 가능한 재고·출고 수량을 정확히 반환하는 것이다.
