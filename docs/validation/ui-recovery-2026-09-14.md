# 화면 예외 처리·복구 검증 — 2026-09-14

## 변경

- 사건·데이터·작업·입고 증거 목록의 로딩, 조회 실패, 성공한 빈 결과를 구분한다. 조회 실패 시 이전 페이지나 0건을 현재 결과로 표시하지 않는다.
- 데이터·작업·증거·대기함·대시보드·준비 상태 조회에 재시도 동선을 제공한다. 사건 등록 실패 안내는 등록 폼에서 표시하고 입력값을 유지한다.
- 사건·데이터·조건·입고 증거·작업·계정·종료 처리의 요청 함수에서 처리 중 중복 제출을 차단한다. 이는 현재 화면의 중복 요청 방지이며 서버 전체의 멱등성 보장을 추가한 것은 아니다.
- 작업의 409 응답 후 변경 폼을 잠그고 `최신 작업 불러오기`로 복구한다. 사유·증빙 초안과 첨부 선택은 유지하고 담당자 선택은 최신 값으로 갱신한다. 현재 사건의 종료 여부도 재조회한다. 내용을 확인한 사용자가 직접 다시 처리하며 자동 재제출하지 않는다.
- 작업 상세 응답은 마지막 선택에만 반영한다. 종료 점검도 이전 조회가 나중에 도착해 최신 점검을 덮어쓰지 않도록 한다.
- 연결 실패는 한국어로 안내한다. 쓰기 요청의 응답을 받지 못하면 반영 여부부터 확인하도록 안내한다.

## 검증 방법과 결과

프론트 타입 검사·빌드와 기존 업무 테스트 통과. 기존 8개 테스트에 [recovery.spec.ts](../../frontend/e2e/recovery.spec.ts)의 7개를 추가했다. 전체 구성은 계산 로직 2개, 기존 브라우저 6개, 예외 처리 브라우저 7개다.

| 시나리오 | 확인한 결과 | 검증 방식 |
| --- | --- | --- |
| 사건 목록 | 다음 페이지 실패 시 이전 행·빈 결과 숨김, 재시도 시 2페이지 복구, 이전 이동 후 빈 결과, 경계 버튼 비활성 | 브라우저에서 합성 페이지 응답·통신 중단 주입 |
| 데이터 목록 | 실패·빈 목록 구분, 페이지 복구·경계, 모바일 가로 넘침 없음 | 합성 페이지 응답·통신 중단 주입 |
| 사건 등록 | 400 뒤 입력 보존, 같은 순간 submit 2회 발생 시 요청 1회, 실제 DB에 사건 1개 | 첫 응답만 합성 거절 후 실제 API 사용 |
| 작업 동시 수정 | 두 번째 로그인 세션이 버전을 변경하면 첫 세션409; 폼 잠금; 사유 유지; 재조회 후 시작 1회·버전2 증가 | 두 독립 세션과 실제 Spring/PostgreSQL |
| 검토 대기함 | 503 뒤 재시도, 빈 결과, 다음 버튼 비활성 | 합성 장애·빈 응답 주입 |
| 업무 대시보드 | 503 뒤 재시도, 빈 결과, 다음 버튼 비활성 | 합성 장애·빈 응답 주입 |
| 사건 작업·입고 증거 | 통신 실패 때 빈 목록 문구 없음, 재시도 후 실제 빈 목록 표시 | 합성 사건 + 조회 통신 중단 후 실제 API 사용 |

기존 업무 테스트는 조건 승인·판정·증거 승인·첨부·담당자 처리·종료 차단·계정 보안과 주요 모바일 화면을 계속 검증한다. 페이지 응답 주입 검증은 서버 페이지 쿼리의 검증을 대체하지 않으며 기존 WorkspaceQueryTests 등이 서버 경계를 검증한다.

## 범위

합성 자료 검증이며 회사의 실제 업무 인수 승인은 아니다. 모든 화면·기기·네트워크 조합을 전수 검증한 것은 아니다. 서버의 판정·권한·버전 충돌 규칙은 변경하지 않았다. AI 연결과 배포는 진행하지 않는다.
